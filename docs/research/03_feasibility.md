# 03. 기술적 타당성 분석

## 1. 기존 CCTV 적용 가능성

| 연동 방식 | 내용 | 적용성 | 리스크 |
|---|---|---|---|
| **RTSP 직접 수신** | IP 카메라/NVR의 RTSP URL에서 H.264/H.265 수신 | 높음 (거의 모든 IP 카메라·NVR 지원) | 카메라당 동시 세션 수 제한, 메인스트림 부하 → **서브스트림(저해상도) 우선 + 이벤트 시 메인스트림** |
| **ONVIF Profile S/T** | 장치 탐색, 스트림 URI 조회, PTZ, 이벤트 구독 (T: H.265·모션 이벤트) | 높음 | 제조사별 구현 편차 |
| **ONVIF Profile M** | 분석 메타데이터(박스·분류·이벤트) 표준 스키마, MQTT 이벤트 | 중간 | 우리 결과를 VMS 타임라인에 **역으로 넣을 때** 유용 |
| **VMS SDK/API** (Milestone, Genetec, 이노뎁 등) | VMS가 영상 재배포·녹화 검색 제공 | 중간 (공공 관제센터는 VMS 경유가 현실적) | 상용 SDK 라이선스, 업체 협조 필요 |
| NVR 녹화 파일 export | MP4 등 | 높음 (MVP 1단계) | 오프라인 전용 |
| 아날로그/HD-TVI | 인코더 필요 | 낮음 | 화질 부족 |

**결론**: 교체 없이 연동 가능. 단, **화질(저화질 노후 CCTV)**이 흉기 탐지의 상한을 결정 → 카메라별 "분석 가능 항목" 프로파일 필요 (예: 저화질 카메라는 흉기 판정 비활성).

> 법적 제약: 개인정보보호법 제25조 — CCTV 녹음 금지 → **오디오 분석은 범위 제외**. 운영 주체(지자체 등)의 목적 내 처리여야 하며, 실증 시 영상 반출·보관 기준 확인 필요.

## 2. 필요한 AI 모델 (후보, 최종 선택은 Phase별 벤치마크 후)

| 기능 | 1순위 후보 | 대안 | 선택 근거 / 주의 |
|---|---|---|---|
| 객체 탐지 (사람·흉기 후보·둔기) | **RF-DETR** (Apache-2.0) | Ultralytics YOLO11/YOLO26 (**AGPL-3.0**/Enterprise), YOLOX (Apache-2.0) | 라이선스: AGPL은 서비스 배포 시 소스공개 의무 → 상용화 가능성 고려 시 Apache 우선. 정확도·속도는 Phase 1에서 실측 비교 |
| 다중 객체 추적 | **BoT-SORT** (MOT17 HOTA 63.8) | ByteTrack (60.5, 처리량 우수), OC-SORT (62.0, 비선형 이동=추격/도주에 유리) | 추격·도주 장면은 비선형 → OC-SORT도 함께 비교 |
| 자세 추정 | **RTMPose** (MMPose, Apache-2.0, COCO 75.8 AP) | RTMO(one-stage), ViTPose | 다인원 실시간, 공격 동작·쓰러짐 특징 추출 |
| 행동 인식 | **골격 기반**(PoseC3D/ST-GCN, MMAction2) | 클립 기반(VideoMAE 등) | 골격 기반은 배경 변화에 강하고 가벼움, 개인정보 측면 유리. 싸움처럼 접촉이 많은 행동은 클립 기반과 비교 |
| 장면 수준 이상 점수 | WSVAD 계열 (CLIP 특징 기반) | – | 보조 신호. 단독 판정 금지 |
| 검증·요약 (VLM) | **Qwen2.5-VL-7B / Qwen3-VL 소형** (오픈 가중치) | InternVL3, NVIDIA VSS (Cosmos 계열) | 상위 이벤트에만 호출. 라이선스는 크기별로 개별 확인 필요 |
| 다중 카메라 Re-ID | OSNet 계열 Re-ID | DeepStream NvDeepSORT, MV3DT | 7단계. 자동 연결이 아닌 후보 제시 |

**버전 정책**: 위 후보의 **정확한 버전은 Phase 1 착수 시 GPU/CUDA 환경 확인 후 고정**하고 `docs/decisions/`에 (버전·선택 이유·대안·호환성) 형식으로 기록. 지금 버전을 확정하면 근거 없는 고정이 됨.

| 근거 수치 | 출처 |
|---|---|
| RTMPose: GTX 1660 Ti 430+ fps (사람 crop 단위) | [S39] |
| Cerberus: L40S 1장 57.7 fps (VLM 캐스케이드) | [S29] |

| 단계 | 권장 구성 (가설) | 비고 |
|---|---|---|
| 개발/MVP (1~5단계, 녹화영상) | 24GB급 GPU 1장 (예: RTX 4090/L4급), 32GB+ RAM | VLM 7B는 양자화 시 24GB 내 구동 가능성 높음 — 실측 필요 |
| 파일럿 (6단계, 실카메라 10~30대) | 48GB급 GPU 1~2장 (L40S급) 또는 상시 파이프라인 GPU + VLM GPU 분리 | 분석 fps를 5~10fps로 낮춰 스트림 수 확보 |
| 운영 확장 | DeepStream/Triton 기반 다중 GPU, 엣지 카메라 1차 필터 결합 | DeepStream 8.0: Ampere~Blackwell, NvDCF/DeepSORT 추적기 내장 |

**측정할 것**: 카메라당 GPU 점유, end-to-end 지연(프레임 수신→알림), VLM 호출률(이벤트/시간) × 호출당 지연.

## 5. 예상 병목 및 기술적 위험

| 위험 | 영향 | 완화 |
|---|---|---|
| R1 흉기 소형·가림으로 미탐/오탐 | 핵심 시나리오 실패 | 흉기는 "증거 중 하나". 고화질 카메라·근거리 한정 프로파일 |
| R2 연출 데이터 ↔ 실영상 도메인 갭 | 실제 성능 급락 | 실 CCTV 정상 영상으로 오탐 별도 측정, 도메인 적응 |
| R3 오탐 과다 → 관제 신뢰 붕괴 | 서비스 실패 | FP/cam-h를 1차 지표로, 위험도 단계별 알림 정책 |
| R4 위험도 임계값의 근거 부족 | 검증 불가 | 04 문서 §4의 평가 구조(PR 기반 운영점, 보정) |
| R5 VLM 환각·지연·비용 | 잘못된 요약, 신고서 오류 | 증거 교차검증, 요약에 "근거 프레임" 링크 필수, 관제자 확인 |
| R6 추적 ID 스위칭(군중·가림) | 관계 추론(추격/도주) 오류 | 관계 판단에 최소 지속시간·ID 신뢰도 반영 |
| R7 RTSP 연결 불안정·지연 | 실시간성 저하 | 재연결, 버퍼 모니터링, 지연 계측 |
| R8 개인정보·법적 이슈 | 실증 불가 | 신원식별 배제, 마스킹 옵션, 보관기간 정책, 실증 전 법률 검토 |
| R9 라이선스 (AGPL, 데이터 약관) | 상용화 제약 | Apache/MIT 우선, 데이터 약관 기록 |
| R10 다중 카메라 재식별 정확도 | 이동경로 오류 | 후보 제시 + 관제자 확정 |
