# 04. 프로젝트 정의 v1

## 1. 한 줄 정의

기존 CCTV 영상에서 **사람 간 관계와 시간 흐름을 근거로 "지금 무슨 상황인가"를 판단**하고, 판단 근거·관련 영상·신고 정보를 정리해 **관제자가 사건을 이해하고 신고 준비를 마치는 시간을 줄이는** 관제 지원 시스템.

## 2. 핵심 기능 (In Scope)

| 영역 | 기능 |
|---|---|
| 입력 | 녹화 파일 → RTSP/ONVIF(S/T) 스트림, 카메라별 메타(위치·구역·화질 프로파일) |
| Perception | 사람·위험물 후보 탐지, 다중 객체 추적, 자세 추정, 골격 기반 행동 인식 |
| **Context/Relation** | 사람 쌍(pair)별 거리·상대속도·접근/이탈·추격 관계, 위험물 보유자 연결, 구역(진입금지 등)·시간대 맥락 |
| **Risk Engine** | 증거 누적형 상황 판정 → 위험 단계(NORMAL~EMERGENCY) + **판단 근거(evidence trace)** |
| 검증·요약 | 상위 단계 이벤트만 VLM으로 검증·요약, 증거와 불일치 시 표시 |
| 관제 Dashboard | 알림 큐(위험도순), 위험 유형·근거, 사건 클립(전후 N초), 타임라인, 주변 CCTV, 관제자 피드백(정탐/오탐) |
| 신고 지원 | 구조화 사건 패키지(시간·위치·유형·위험물·인원·행동·이동방향·관련 CCTV·클립·AI 근거) — **관제자가 확인·수정 후 신고** |
| 평가 | event-level 지표, 지연, 사용자 실험 도구 |

## 4. Risk Engine 설계 원칙 (임계값을 임의로 확정하지 않는 구조)

```
Perception 출력(트랙·자세·객체)
   → 특징 추출 (개인: 행동확률, 위험물 보유확률, 쓰러짐 / 쌍: 거리, 상대속도, 접근·이탈, 추격 / 장면: 구역, 시간대, 밀집도)
   → 상황 패턴 매칭 (시간 윈도우 내 시퀀스: 예 "위험물 보유 + 접근 → 상대 이탈/도주 → 추격")
   → 상황 점수 s ∈ [0,1]  (v0: 해석 가능한 규칙/가중 모델 → v1: 학습 모델(GBDT/작은 시계열 모델)로 교체 비교)
   → 확률 보정 (Platt/Isotonic, 검증셋)
   → 단계 매핑 = 운영정책 (설정 파일, 코드에 하드코딩 금지)
```

- **v0 규칙의 가중치·임계값은 "초기 가설값"으로 명시**하고 결과물에 그렇게 표기.
- 단계 경계는 검증셋 **PR 곡선에서 운영점으로 선택**: 예) EMERGENCY = 정밀도 우선 운영점, ATTENTION = 재현율 우선 운영점. 목표값(예: 최소 재현율)은 관제 측과 합의한 **정책 입력**.
- 장소·카메라별 보정 가능 구조(같은 점수라도 학교 앞/야간은 정책 다름).
- 모든 판정은 증거 리스트를 남김 → 오류 분석·관제자 설명에 사용.
- 관제자 피드백(정탐/오탐)을 저장해 재보정 데이터로 사용.

### 평가 프로토콜

| 수준 | 지표 |
|---|---|
| 모듈 | 탐지 mAP(특히 흉기 소형객체 분리), 추적 HOTA/IDF1, 자세 AP, 행동 F1 |
| **이벤트 수준 (주 지표)** | 시간 구간 매칭(tIoU 기준) 기반 Precision / Recall / F1, PR 곡선·AP, FNR |
| 운영 | **FP / 카메라·시간**, 탐지 지연(사건 시작 → 알림), 위험 유형별·조건별(주야간·밀집) 분리 |
| Ablation | 관계 특징 유무, 시간 윈도우 길이, VLM 유무 (D1·D2 가설 검증) |
| 서비스 KPI | 사건 인지 시간, 상황 파악 시간, 신고 준비 시간, 전체 대응 시간, 신고 정보 정확도 |

서비스 KPI 측정: 동일 사건 영상 세트로 **기존 방식(다채널 VMS 화면) vs 본 시스템** 사용자 실험(within-subject, 관제 경험자 또는 대리 참여자).

데이터 분할: 카메라/장소 단위로 train/val/test 분리(같은 장소 누수 금지), **정상-유사 hard negative를 test에 별도 포함**.

## 5. MVP 정의

**MVP = 1~5단계를 녹화 영상으로 완주** (실카메라 연동 전)
- 입력: AI-Hub + 공개 데이터 + 자체 hard negative 영상
- 출력: 위험도·근거가 붙은 이벤트, 웹 대시보드, 사건 패키지 초안
- 성공 판정: 이벤트 수준 평가 리포트 + 소규모 사용자 실험 결과 (수치 목표는 Phase 0에서 베이스라인 측정 후 설정)

## 6. 최종 시스템 아키텍처

```
[IP CCTV / NVR / VMS]
   │ RTSP (sub-stream 상시, main-stream 이벤트시) · ONVIF S/T
   ▼
[Ingest Service] ── 디코딩(GPU), 프레임 샘플링, 링버퍼(사건 전후 영상 확보)
   ▼
[Perception Pipeline]  Detection → Tracking → Pose → Action   (GPU, 카메라별 프로파일)
   │ 트랙/이벤트 메타데이터 (메시지 버스)
   ▼
[Context & Relation Builder] 개인·쌍·장면 특징, 구역/시간 맥락
   ▼
[Risk Engine] 패턴 매칭 → 점수 → 보정 → 정책 기반 단계 → evidence trace
   │ (WARNING 이상)
   ├──▶ [VLM Verifier/Summarizer] 클립+증거 → 요약, 증거 정합성 체크
   ▼
[Incident Service] 사건 생성·병합, 클립 저장, 타임라인, 주변 CCTV 후보(카메라 토폴로지 + Re-ID)
   ▼
[API (REST/WebSocket)] ──▶ [관제 Dashboard] 알림·영상·타임라인·지도·피드백
                         └▶ [신고 지원] 사건 패키지 (관제자 확인 → 사람이 신고)
[Storage] 메타데이터 DB · 클립 저장소 · 감사 로그     [Eval] 지표·리포트
(옵션) ONVIF Profile M / VMS 연동으로 결과를 기존 VMS 타임라인에 게시
```

## 7. 개발 단계 (각 단계는 Gate 통과 후 진행)

| 단계 | 산출물 | Gate (측정 후 판단) |
|---|---|---|
| **0. 준비** | 데이터 확보(AI-Hub 신청), 평가 프로토콜·라벨 스키마, GPU 환경 확정·버전 기록, 정상-유사 시나리오 목록 | 평가 스크립트로 더미 결과 산출 가능 |
| **1. 탐지** | 녹화영상 → 사람/위험물 후보 탐지, 후보 모델 2~3종 비교 | 흉기 크기별 mAP·FP 측정 → 흉기를 어느 조건에서 증거로 쓸지 결정 |
| **2. 추적+행동** | 추적·자세·행동 인식, 쌍 관계 특징 | HOTA/IDF1, 행동 F1, 관계 특징(추격·도주) 정확도 |
| **3. Risk Engine** | v0 규칙 → v1 학습형, 보정, 평가 리포트 | 이벤트 F1·FP/cam-h, ablation으로 관계 특징 효과 확인 (D1) |
| **4. Dashboard** | 알림 큐·영상·타임라인·피드백 | 사용자 파일럿(소수)으로 사용성 확인 |
| **5. 사건 확보+요약+신고 지원** | 링버퍼 클립, VLM 요약(검증 포함), 사건 패키지 | 요약 사실 정확도, 신고 준비 시간 A/B (D2·D4·D5) |
| **6. 실 IP CCTV** | RTSP/ONVIF 연동, 지연 계측 | E2E 지연, 장시간 안정성, 실영상 FP/cam-h |
| **7. Multi-Camera** | 카메라 토폴로지, Re-ID 후보 제시, 이동경로 | 후보 Top-k 정확도, 관제자 확인 시간 |

## 8. 검토 요청 사항 (사용자 결정 필요)

1. 상용화 가능성 고려 여부 → AGPL(Ultralytics) 사용 가능 여부 결정
2. 사용 가능한 GPU 환경 (로컬/클라우드, 모델명)
3. 실증 협력처(지자체 관제센터·학교 등) 가능성 → 실 영상·사용자 실험 대상
4. 1차 집중 시나리오 우선순위 (제안: ① 폭행/싸움 ② 쓰러짐 ③ 흉기 위협+도주/추격)
5. AI-Hub 데이터 신청 진행 가능 여부
